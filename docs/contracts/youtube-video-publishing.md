# YouTube video publishing — SYN-SOC-006

**Status:** SYN-SOC-006 merged in [PR #37](https://github.com/synvaro/synvaro/pull/37). SYN-SOC-006A safety correction: Implemented — PR pending review. This is an explicit owner-controlled upload of one saved, same-Brand MP4 to a connected YouTube channel. An assembled Reel is an eligible source. No scheduling, automatic upload, or separate Shorts API exists.

Official references checked **2026-10-28**: [videos.insert](https://developers.google.com/youtube/data/reference/rest/v3/videos/insert), [resumable protocol](https://developers.google.com/youtube/data/guides/using_resumable_upload_protocol), [videos resource](https://developers.google.com/youtube/data/reference/rest/v3/videos), [Google OAuth web server](https://developers.google.com/identity/protocols/oauth2/web-server), [Shorts eligibility](https://support.google.com/youtube/answer/15424877?hl=en). The actual Google application, consent-screen audit, quotas and channel entitlement require separate live verification. The current reference states `videos.insert` consumes one unit of the Video Uploads quota bucket and limits calls to 100/day; account-specific quotas may differ.

`READY` is a local review intent. `PUBLISHING` identifies one claimed attempt; an interrupted claim becomes `UNCERTAIN`. `PROCESSING` means YouTube returned a video ID but has not yet confirmed processing success. `PUBLISHED` means a read-only lookup verified the ID, channel and privacy; it does **not** mean public visibility for private/unlisted uploads. `FAILED` is a definite provider rejection. Resume and check are explicit actions against the existing encrypted session/known video ID. No request starts a second session for an uncertain intent.

## SYN-SOC-006A — Upload safety repair

| ID | Acceptance rule | Evidence subject |
|---|---|---|
| YT-FIX-001 — Single transfer owner | A PostgreSQL owner UUID is conditionally claimed for one publication. Each progress/result write and each further provider call checks ownership. Reading a `PUBLISHING` row never makes it resumable because a timestamp aged out, even after five minutes. Lease expiry is diagnostic only. A normal timeout or rejection releases ownership **after** provider I/O returns. A crash leaves the row blocked. An operator may release a stale claim only after independently confirming the old process has terminated and no PUT remains in flight; the existing encrypted session is then probed and only the provider-confirmed offset is resumed. If no such proof is available, fail closed. | Two API instances, delayed PUT older than the lease, premature resume, fenced worker, expired lease, audited release, same-session 308 offset; zero extra `videos.insert` or PUT while active. |
| YT-FIX-002 — Known video ID | The final upload response ID is committed before read-only `videos.list` verification. If verification fails, the ID remains `UNCERTAIN`. `resume` cannot send bytes or initiate a session once the ID is known; `check` only verifies channel, privacy and processing state. | Verification outage, repeated resume, later successful check and unchanged upload counters. |
| YT-FIX-003 — Regression | Session, Origin, Brand, channel, source, duplicate confirmation and provider error rules continue to apply. A fresh PostgreSQL migration adds owner and diagnostic lease fields without changing existing publication records or endpoints. | Clean migration, real PostgreSQL tests, full CI gates. No real YouTube upload or browser UI change in this correction. |

Operator command after independently verifying process termination and absence of any in-flight PUT: `DATABASE_URL=... node scripts/release-abandoned-youtube-transfer.mjs <publication-id> <evidence> <operator>`. The evidence and operator are persisted with an audit UUID. Never invoke this solely because the lease timestamp expired. If the session is missing or a video ID is already known, use a separate evidence-based resolution or read-only `check`; do not create another upload session. The owner token and encrypted session never appear in API responses.
